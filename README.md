# 이카운트 재고 감시 · 대조 시스템 (ECOUNT)

이카운트(ECOUNT)가 POV의 **단일 재고 원본(진실)** 이다. 하나의 이카운트 안에서 창고(재고 pool)가
나뉜다: **[오프라인 창고]** / **[온라인(MXN) 창고]**. 온라인 채널(자사몰=Cafe24, 29CM, 카카오,
올리브영)이 실제로 꺼내 파는 실물은 온라인(MXN) 창고에 있다.

이 시스템은 이카운트 재고를 매일 읽어 **채널 표시재고와 대조**하고, 어긋난 곳을 찾아 알린다.
온라인(Cafe24) 시스템의 구글시트/슬랙/스케줄 인프라를 재활용한다.

## POV 재고 구조 (확정)

- **오프라인 재고** — 매장창고 **2곳**. 이카운트에 각각 창고로 설정됨.
- **온라인 재고** — 물리적으로는 **MXN 창고 한 곳**에 있으나, **채널별로 재고를 분리 운영**한다.
  MXN과 이카운트 양쪽에서 채널별(자사몰/29CM/카카오/올리브영) 창고로 나뉘어 있음.
  → 통합재고관리를 위해 OMS 도입 검토 중. **이 대조 시스템이 그 전까지의 다리.**

### ②번이 왜 대량 발생하나 (핵심)

온라인은 **한 물리 창고를 채널별 창고로 쪼개 놓은** 구조다. 그래서 어떤 상품이 **자사몰(Cafe24)
슬라이스에서는 0(품절)** 인데, **같은 실물이 다른 채널 슬라이스 / 미배분분으로 MXN에 남아 있는**
상황이 매일 생긴다. 손님은 사려는데 채널은 품절 → 흘리는 매출. 대조가 바로 이걸 드러낸다.

### 매칭 키 (대조의 연결고리) — 품목코드로 확정

**바코드 매칭은 불가** (Cafe24에 바코드 미입력 품목이 많음). → **품목코드로 매칭**한다.

Cafe24는 `product_code`(P0000…, 상품 레벨)·`variant_code`(P0000…000C, 옵션 레벨) 두 층이 있다.
probe 때 이카운트 품목코드를 보고 아래 2가지를 확정:
1. **직접 일치 vs 매핑표** — 이카운트 품목코드가 Cafe24 코드와 문자열이 같으면 바로 조인,
   다르면 이카운트 품목코드 ↔ Cafe24 코드 **매핑표**를 둔다.
2. **레벨** — 이카운트 품목이 옵션(SKU) 단위면 `variant_code`와, 상품 단위면 `product_code`와
   맞춘다. 재고는 옵션별로 갈리므로 가능하면 옵션 레벨로 대조.

## 핵심 모델 — 재고 감시(대조) 레이어

매출 10배 규모 동종업체가 엑셀로 운영하는 3층 구조를 POV용으로 옮긴 것. 주문을 처리하는
자동화가 아니라 **틀어진 곳을 매일 찾아내는 감시 레이어**다. OMS 도입 전까지의 다리.

```
이카운트 [온라인(MXN) 창고] 가용재고   ←→   Cafe24 채널 재고
        (API로 자동 수집)                    (이미 매일 자동 수집 중)
                        │
              차이 → 상태 → 발주우선순위
                        │
      ┌─────────────────┴─────────────────┐
 ① Cafe24 재고 수정 필요 리스트   ② MXN엔 있는데 Cafe24엔 품절 ← 흘리는 매출
```

- **가용재고**(실물 − 예약/기주문분)를 비교한다 → 사실상 "주문 반영 이후 지금 팔 수 있는 수량".
- **②번이 핵심**: 창고엔 팔 수 있는데 채널은 품절로 손님을 돌려보내는 상품. 재고를 채널별로
  나눠두면 매일 대량 발생. 이 리스트만 매일 뽑아도 매출이 움직인다.
- 첫 타겟 = **이카운트(온라인창고) vs Cafe24** (양쪽 다 이미 자동 수집 가능). 29CM·카카오·
  올리브영은 그다음 확장.

### 스냅샷 타이밍 (중요)

주문 배치 마감이 **오전 10시**다. 오전 10시까지 완료된 주문만 모아 그날 MXN(이카운트
온라인창고)에 넘겨 가용재고를 갱신한다. 따라서 대조 스냅샷은 **10시 배치가 이카운트에 반영된
뒤**에 찍어야 양쪽이 같은 기준이 된다.

## DOI 기반 우선순위 체계 (2026-07-28 확정, 온라인 시스템과 동일 패턴)

기존 설계엔 "판매 속도" 개념이 없어서 재고량만으로 저재고를 판정했는데, 이러면 "재고는 적지만
잘 안 팔려서 여유 있는 것"과 "재고도 적은데 빨리 팔려서 곧 품절될 것"을 구분 못 한다. 온라인
알림 시스템(카페24)이 이미 쓰고 있는 **DOI(Days of Inventory, 재고소진예상일수)** 체계를
그대로 오프라인에 적용한다.

**DOI 계산식**: `DOI = 재고수량 ÷ (최근7일판매량 ÷ 7)` (일평균판매량 기준). 최근7일판매량이
0이면 DOI는 정의 안 됨(무한대) — 이 경우 "재고소량·판매없음"이나 "품절" 분기로 별도 처리.

**⚠️ 위험/주의 임계값은 조달유형별 리드타임 기준으로 차등 적용** (온라인 시스템의
DOI≤5일/5~10일 평탄 기준을 그대로 쓰면 안 됨 — 그건 빠른 사입 재발주 전제. 오프라인은
품목마다 조달유형이 다르고 실제 리드타임도 다름 — 자체제작 4~6주, 국내사입 최대 1주,
해외수입 2~10주(대표값 3주로 단순화). 온라인봇과 다른 채널이라 기준이 달라도 됨 — 의도적 결정):

| 조달유형 | 리드타임 | 위험(DOI≤) | 주의(DOI) |
|---|---|---|---|
| 자체제작 | 5주(35일) | 35일 | 35~49일 |
| 국내사입 | 1주(7일) | 7일 | 7~14일 |
| 해외수입 | 3주(21일) | 21일 | 21~35일 |

| 상태 | 조건 | 3층 결과물 |
|---|---|---|
| 위험 | DOI ≤ 위 표의 조달유형별 위험선 — 지금 발주 안 하면 리드타임 내 재고 바닥 | `디자인팀_발주필요` (DOI 오름차순) |
| 주의 | DOI가 위 표의 주의 구간 — 곧 발주 준비 필요 | `디자인팀_발주필요` |
| 재고소량·판매없음 | 재고 1~5개 & 최근7일판매량 0 | `디자인팀_발주필요` |
| 품절-신규 | 재고 0, 품절경과일 0~9일 | `디자인팀_발주필요` (즉시 재입고) |
| 품절-지속 | 재고 0, 품절경과일 10~29일 | `디자인팀_발주필요` (재입고 골든타임, 최근90일판매량 내림차순) |
| 품절-장기 | 재고 0, 품절경과일 30일+ | 최근90일판매량>0 → `디자인팀_발주필요` / =0 → `악성품절` |
| 과잉 | DOI > 180일(약 6개월) — 재고 대비 판매 속도가 너무 느림 | `관리팀_전체재고`에 상태 표시 + `악성재고` 후보 |
| 초과주문 | 재고수량 < 0 | 최우선 확인 (데이터 오류 가능성) |
| 정상 | 그 외 | — |

**품절경과일 계산**: 전날 `일별재고이력`에서 같은 품목코드의 상태가 이미 품절 계열이었으면
+1, 재입고(재고>0)로 돌아오면 0으로 리셋. 매일 이전 행을 참조하는 상태 저장형 계산이 필요.

**조달유형 자동 매칭(2026-07-28 확정)**: SKU마다 일일이 분류하지 않는다. 조달유형은 사실상
**브랜드 단위 속성**이라(POV 자체 브랜드=항상 자체제작, 특정 해외 브랜드=항상 해외수입 등),
별도 **브랜드마스터**(브랜드명↔조달유형↔기본리드타임, 브랜드 수십 개 수준) 참조표를 하나
두고, `품목마스터` 생성 시 품목코드→브랜드(이카운트에서 자동 추출)에 이 표를 조인해서
조달유형·리드타임을 자동으로 채운다. 브랜드마스터에 없는 새 브랜드는 `미분류`로 표시되어
눈에 띄고, 사람이 그 브랜드 하나만 한 번 분류하면 그 뒤로 해당 브랜드의 모든 SKU(신상품
포함)에 영구 자동 적용된다. 브랜드마스터는 아직 미구현 — `ecount_daily_runner.py` 또는
품목마스터 생성 스크립트에서 다음 단계로 구현 예정.

**악성재고 vs 악성품절 — 반대 축**:
- 악성재고: 재고 많음 + 오래 안 팔림 (과잉)
- 악성품절: 재고 없음(0) + 오래 방치(30일+) + 최근90일판매량 0(부활가치 없음) (방치)
같은 "품절-장기" 안에서도 최근90일판매량으로 나뉜다 — 판매량 있으면 재입고 가치 있음
(`디자인팀_발주필요`), 없으면 진짜 단종 후보(`악성품절`).

## 재고변동(입출고) 자동화 최종 설계 (2026-07-27 확정)

**배경**: 이카운트 OAPI 전체에 재고변동/입출고 조회 API가 없음(확정, 위 "OAPI 조회 API 전수
확인" 참고). 대신 이카운트 화면의 **"자동알림설정"** 기능(판매현황 화면 Option 메뉴에 존재
확인됨)으로 매일 이메일 발송을 예약해서 완전자동화한다.

**데이터 조합**:
1. **재고수량 / 전일재고** — 이미 인증된 `창고별재고현황` API로 매일 스냅샷 (완전자동, 기존)
2. **출고수량(판매량)** — `판매현황` 화면의 자동알림설정으로 매일 이메일 발송 예약
   (조건: 반복 매일, 기준일자=**전일**, 창고 필터 없음, 발송시각 **01:00**) →
   저희 자동화가 Gmail에서 매일 첨부 엑셀을 읽어 품목별 출고수량 집계
3. **입고수량** — 별도 데이터 없이 **계산으로 도출**:
   `입고수량 = (오늘재고 − 전일재고) + 출고수량`
   부수효과: 이 계산 결과가 비정상(음수 등)이면 판매현황 입력 누락/지연 신호로 활용 가능
   (데이터 정합성 자체 점검 장치)

**판매현황 엑셀 실제 컬럼 확인됨** (`업로드 테스트로 검증 완료`):
`일자 / 품목그룹2명(브랜드) / 품목코드 / 품명 및 규격 / 수량 / 단가 / 공급가액 / 부가세 /
합계 / 적요 / 창고명 / 사원(담당)명` — 브랜드·창고 정보가 이미 포함되어 있어 별도 매핑 불필요.

**타이밍 검증**: 온라인 출고입력은 매일 14~19시, 오프라인은 매장 영업(11~20:30) 기준 —
자정 이후 조회 시 "전일" 데이터는 온라인/오프라인 모두 이미 완결된 상태라 안전. 채널별로
스케줄을 나눌 필요 없이 **단일 규칙**으로 충분(2026-07-27 논의로 확정, 최초엔 채널별 분리
제안했으나 기각).

**오프라인 재고 뷰 구조 — 보는 사람 기준으로 탭 분리** (2026-07-27 정정):
- **디자인팀 탭** — 발주(제작) 필요 품목만 필터링된 액션 리스트. 전체 재고는 안 보여주고
  "만들어야 하는 것"만. 창고별 상세는 불필요(발주 여부만 판단하면 되므로).
- **관리팀 탭** — 전체 재고 현황(모든 브랜드·품목, 필터 없음). 관리팀이 실제 발주를 담당하므로
  전체 그림 필요. 기본은 품목합계(전체 오프라인 창고 합산), 필요시 창고별상세로 드릴다운
  ("실물이 어디 있는가", 매장 간 재배치 검토용).

## 이카운트 OAPI 조회(read) API 전수 확인 결과 (2026-07-27)

**대안 (택 1, 결정 대기 중)**:
1. 이카운트 재고변동표 화면에 예약메일(스케줄 리포트 발송) 기능이 있으면 → 그 메일을 자동
   파싱해서 완전자동화 (사용자가 화면에서 해당 버튼 확인 중)
2. 없으면 → 사람이 매일 재고변동표 엑셀을 다운받아 업로드(구글드라이브 등)하는 반자동 방식

### 3. 설정
`ecount_config.example.json`을 `ecount_config.local.json`으로 복사해 지정 품목·브랜드·채널을 채운다.

## 설계 메모

- **재고변동표 endpoint**: 정확한 path는 로그인 후 이카운트 API 문서에서 확인 필요.
  현재 클라이언트는 `InventoryBalance/GetListInventoryBalanceStatusByLocation`(창고별 재고현황)을
  기본 편의 메서드로 제공. 재고변동(수불) 전용 endpoint가 있으면 `--endpoint`로 확인 후 확정.
- **도메인**: 테스트 `sboapi{ZONE}.ecount.com`, 운영 `oapi{ZONE}.ecount.com`.
