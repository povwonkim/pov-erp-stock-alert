# 이카운트 재고 감시 · 대조 시스템 (ECOUNT)

이카운트(ECOUNT)가 POV의 **단일 재고 원본(진실)** 이다. 하나의 이카운트 안에서 창고(재고 pool)가
나뉜다: **[오프라인 창고]** / **[온라인(MXN) 창고]**. 온라인 채널(자사몰=Cafe24, 29CM, 카카오,
올리브영)이 실제로 꺼내 파는 실물은 온라인(MXN) 창고에 있다.

이 시스템은 이카운트 재고를 매일 읽어 **채널 표시재고와 대조**하고, 어긋난 곳을 찾아 알린다.
온라인(Cafe24) 시스템의 구글시트/슬랙/스케줄 인프라를 재활용한다.

## POV 재고 구조 (확정)

- **오프라인 재고** — 매장창고 **2곳**. 이카운트에 각각 창고로 설정됨.
- **온라인 재고** — 물리적으로는 **MXN 창고 한 곳**에 있으나, **채널별로 재고를 분리 운영**한다.
  MXN과 이카운트 양쪽에서 채널별(자사몰/29CM/카카오/올리브영) 창고로 나뉘어 있음.
  → 통합재고관리를 위해 OMS 도입 검토 중. **이 대조 시스템이 그 전까지의 다리.**

### ②번이 왜 대량 발생하나 (핵심)

온라인은 **한 물리 창고를 채널별 창고로 쪼개 놓은** 구조다. 그래서 어떤 상품이 **자사몰(Cafe24)
슬라이스에서는 0(품절)** 인데, **같은 실물이 다른 채널 슬라이스 / 미배분분으로 MXN에 남아 있는**
상황이 매일 생긴다. 손님은 사려는데 채널은 품절 → 흘리는 매출. 대조가 바로 이걸 드러낸다.

### 매칭 키 (대조의 연결고리) — 품목코드로 확정

**바코드 매칭은 불가** (Cafe24에 바코드 미입력 품목이 많음). → **품목코드로 매칭**한다.

Cafe24는 `product_code`(P0000…, 상품 레벨)·`variant_code`(P0000…000C, 옵션 레벨) 두 층이 있다.
probe 때 이카운트 품목코드를 보고 아래 2가지를 확정:
1. **직접 일치 vs 매핑표** — 이카운트 품목코드가 Cafe24 코드와 문자열이 같으면 바로 조인,
   다르면 이카운트 품목코드 ↔ Cafe24 코드 **매핑표**를 둔다.
2. **레벨** — 이카운트 품목이 옵션(SKU) 단위면 `variant_code`와, 상품 단위면 `product_code`와
   맞춘다. 재고는 옵션별로 갈리므로 가능하면 옵션 레벨로 대조.

## 핵심 모델 — 재고 감시(대조) 레이어

매출 10배 규모 동종업체가 엑셀로 운영하는 3층 구조를 POV용으로 옮긴 것. 주문을 처리하는
자동화가 아니라 **틀어진 곳을 매일 찾아내는 감시 레이어**다. OMS 도입 전까지의 다리.

```
이카운트 [온라인(MXN) 창고] 가용재고   ←→   Cafe24 채널 재고
        (API로 자동 수집)                    (이미 매일 자동 수집 중)
                        │
              차이 → 상태 → 발주우선순위
                        │
      ┌─────────────────┴─────────────────┐
 ① Cafe24 재고 수정 필요 리스트   ② MXN엔 있는데 Cafe24엔 품절 ← 흘리는 매출
```

- **가용재고**(실물 − 예약/기주문분)를 비교한다 → 사실상 "주문 반영 이후 지금 팔 수 있는 수량".
- **②번이 핵심**: 창고엔 팔 수 있는데 채널은 품절로 손님을 돌려보내는 상품. 재고를 채널별로
  나눠두면 매일 대량 발생. 이 리스트만 매일 뽑아도 매출이 움직인다.
- 첫 타겟 = **이카운트(온라인창고) vs Cafe24** (양쪽 다 이미 자동 수집 가능). 29CM·카카오·
  올리브영은 그다음 확장.

### 스냅샷 타이밍 (중요)

주문 배치 마감이 **오전 10시**다. 오전 10시까지 완료된 주문만 모아 그날 MXN(이카운트
온라인창고)에 넘겨 가용재고를 갱신한다. 따라서 대조 스냅샷은 **10시 배치가 이카운트에 반영된
뒤**에 찍어야 양쪽이 같은 기준이 된다.

| 시스템 | 실행 시각(KST) | 이유 |
|---|---|---|
| 카페24 재고알림 (기존) | 09:00 | 카페24 자체 재고 스캔 |
| 이카운트↔카페24 대조 (신규) | 10:30~11:00 | 10시 주문배치가 MXN에 반영된 후 |

## 탐사 결과 (2026-07-27, `ecount_probe.py --inventory`, MODE=prod)

**응답 구조**: `Data.Result` (리스트) + `Data.TotalCnt`. 레코드 필드:
`WH_CD`(창고코드) / `WH_DES`(창고명) / `PROD_CD`(품목코드) / `PROD_DES`(품목명) /
`PROD_SIZE_DES`(사이즈) / `BAL_QTY`(재고수량, **문자열** `"1.0000000000"` 형태, **음수 존재**).

**⚠️ 페이지네이션 의심**: `Data.TotalCnt` = `Result` 건수 = **정확히 10000건**. 우연히 딱 맞을
가능성은 낮음 — API가 10000건에서 잘렸을 가능성 높음. 다음 세션에서 확인 필요:
이카운트 API 문서(로그인 후 열람)에서 `InventoryBalance/GetListInventoryBalanceStatusByLocation`의
페이지 파라미터(예: `PAGE_NO`, `PAGE_SIZE` 등) 확인하고 `ecount_client.py`에 페이징 루프 추가.

**창고 목록 (15개, 실제 probe 결과)**:
```
29CM · MXN · MXN(29cm) · MXN(온라인) · MXN(카카오) · OTS · OY ·
POINT OF VIEW (법인) · POP-UP · POV · THE HYUNDAI SEOUL · orer.archive ·
시시호시-수원점 · 신세계 강남-피숀 · 카카오 선물하기(세트 재고)
```
README 위쪽의 "오프라인 매장창고 2곳"보다 훨씬 다양하게 나옴(백화점 입점/편집숍/POP-UP 다수 포함).
→ **확정 필요**: 어느 창고가 "MXN 온라인 물리창고"이고 어느 게 "온라인 채널별 슬라이스"
(`MXN(온라인)`=자사몰/Cafe24 추정, `MXN(29cm)`=29CM, `MXN(카카오)`=카카오 추정 — 사용자 확인 필요),
어느 게 진짜 오프라인 매장/팝업인지.

**품목코드(PROD_CD) 규칙 미확정**: 자릿수·형식이 제각각(`0001004878306`, `001`, `001001`,
`0019-99900-B` 등). 브랜드 구분용 접두어 규칙이 있는지 사용자 확인 필요 —
없다면 브랜드 매칭은 품목명/품목분류 등 다른 필드로 해야 함.

## 이카운트 OAPI 조회(read) API 전수 확인 결과 (2026-07-27)

API 매뉴얼(오픈 API 이용방법, 전송기준표)까지 전부 확인. **이카운트 OAPI V2 전체에 조회(read)
API는 딱 4개뿐**: `발주서조회` / `품목조회` / `재고현황` / `창고별재고현황`. 판매·구매·생산·
재고변동(수불) 관련 API는 전부 **입력(쓰기) 전용**이고 대응하는 조회 API가 존재하지 않음.
→ "재고변동표"(입고수량/출고수량 포함)를 API로 자동 수집하는 것은 **이카운트 쪽에 해당
API가 아예 없어서 불가능**. 승인/신청 문제가 아니라 기능 자체가 없음 — 이 결론은 확정.

**대안 (택 1, 결정 대기 중)**:
1. 이카운트 재고변동표 화면에 예약메일(스케줄 리포트 발송) 기능이 있으면 → 그 메일을 자동
   파싱해서 완전자동화 (사용자가 화면에서 해당 버튼 확인 중)
2. 없으면 → 사람이 매일 재고변동표 엑셀을 다운받아 업로드(구글드라이브 등)하는 반자동 방식

## POV 자체제작 브랜드 재고 트래킹 (`ecount_brand_stock.py`)

디자인팀이 발주 필요 품목을 볼 수 있도록, 품목그룹2(브랜드) 기준으로 필터링한 재고 뷰를 추가.
POV 자체제작 브랜드 목록(품목그룹2명 기준, 이카운트 확인):
`POV_original` / `POV Atelier` / `POV x Hello Kitty` / `POV x KBP` / `POV_한글박물관` /
`POV_collaboration` / `POV_inventario` / `PRESSPRESS` / `PRESSPRESS_collaboration` / `양지사`

이카운트에서 내보낸 재고변동표(또는 품목등록) 엑셀을 입력받아 위 브랜드만 필터링하고 저재고
품목을 표시한다:
```bash
python3 ecount_brand_stock.py --source 재고변동표.xlsx --threshold 10
```
품목그룹2 필드는 OAPI(`품목조회`)로도 나오지만 **CLASS_CD2(코드)만 주고 이름은 안 줌** +
현재 이 계정엔 `품목조회` API 인증이 안 되어 있어서, 당분간은 이카운트 화면에서 내려받은
엑셀(코드 아닌 실제 브랜드명 포함)을 그대로 쓴다.

## 시작 방법

### 1. 인증정보 준비
이카운트 로그인 → **Self-Customizing → 정보관리 → API 인증키발급** 으로 인증키를 발급받고,
아래 중 한 방법으로 설정 (인증키는 절대 커밋 금지 — `.secrets/`는 gitignore됨):

**로컬 파일** `.secrets/ecount.json`:
```json
{
  "COM_CODE": "회사코드",
  "USER_ID": "API용 사용자ID",
  "API_CERT_KEY": "발급받은 인증키",
  "MODE": "test"
}
```
또는 **환경변수** `ECOUNT_COM_CODE` / `ECOUNT_USER_ID` / `ECOUNT_API_CERT_KEY` / `ECOUNT_MODE`.
(운영 전환 시 `MODE`를 `prod`로. 자동화는 온라인처럼 GitHub Secrets 사용 예정.)

### 2. 인증 검증 & 구조 탐사
```bash
python3 ecount_probe.py --check       # Zone+로그인 정상 동작 확인
python3 ecount_probe.py --inventory   # 재고현황 실제 응답 구조 덤프
```
덤프는 `cron_tracking/ecount/`에 저장(gitignore). 여기서 확인한 실제 필드명으로 파서를 만든다.

### 3. 설정
`ecount_config.example.json`을 `ecount_config.local.json`으로 복사해 지정 품목·브랜드·채널을 채운다.

## 설계 메모

- **재고변동표 endpoint**: 정확한 path는 로그인 후 이카운트 API 문서에서 확인 필요.
  현재 클라이언트는 `InventoryBalance/GetListInventoryBalanceStatusByLocation`(창고별 재고현황)을
  기본 편의 메서드로 제공. 재고변동(수불) 전용 endpoint가 있으면 `--endpoint`로 확인 후 확정.
- **도메인**: 테스트 `sboapi{ZONE}.ecount.com`, 운영 `oapi{ZONE}.ecount.com`.
